# 你宠啥 · 商家端移动应用（iOS + Android）技术方案

> 版本 v1.0 · 2026-10-27
> 目标：把现有「商家调度台」（Web 后台）变成 iOS + Android 双端可安装的原生应用，功能与 Web 完全一致。

---

## 一、结论先行

**推荐方案：Capacitor 7 混合架构（复用现有 Vue 3 代码，一套源码打包 iOS + Android）。**

| 判断维度 | 结论 |
| --- | --- |
| 工期 | **约 4 周 / 1 人**（不含商店审核等待） |
| 代码复用 | **业务代码 100% 复用**，只需新增「移动端适配层 + 原生能力桥接」 |
| 后续维护 | Web 与 App 同源，改一处两端生效，不会出现「网页改了 App 没改」 |
| 体验 | 表单/表格/图表类后台场景与原生几乎无差别；弱在复杂手势动画（本场景不需要） |
| 风险 | 可控：主要风险集中在推送（国内需厂商通道）与 iOS 分发（需 Apple 开发者账号） |

**不推荐**在这个阶段用 React Native / Flutter 重写：那等于把 11 个页面、40+ 接口的调用逻辑、图表与表格全部重做一遍，工期翻 4 倍，且从此要维护 Web 与 App 两套界面代码。

## 二、现状盘点（决定方案的前提）

### 2.1 已有资产

| 项 | 现状 |
| --- | --- |
| 前端 | Vue 3.5 + Vite 6 + Element Plus 2.9 + Pinia + ECharts 5 + axios |
| 页面 | 11 个：登录、营业大盘、订单管理、售后管理、商品管理、批量导入、分类管理、库存管理、用户管理、用户访问、配置管理 |
| 后端 | Express + Prisma + MySQL，JWT 鉴权，40+ 接口，部署在微信云托管 |
| 产物 | `index` 主包 1.06 MB（gzip 350 KB），大盘分包 536 KB（gzip 180 KB） |
| 已有移动端基础 | 本轮已加入：侧栏抽屉、`mobile.css` 适配层、`viewport-fit=cover`、弹窗整页化、44px 触控 |

### 2.2 这个后台的交互特征（选型依据）

- **重表单、重表格、重图表，几乎没有转场动画** —— 这正是 WebView 最擅长的场景。
- **只有商家用，不是消费者端** —— 不需要极致首屏速度与丝滑手势。
- **更新频繁**（这几周每周都在加功能）—— 混合方案能让 Web 与 App 同一天更新。
- **需要几个原生能力**：推送（订单提醒）、语音播报、文件选择（批量导入）、安全存储（token）。

## 三、四种方案对比

| | A. Capacitor 混合 ⭐推荐 | B. React Native / Expo | C. Flutter | D. uni-app / Taro |
| --- | --- | --- | --- | --- |
| 现有代码复用 | **100%** | 0（界面全重写） | 0（界面全重写） | 30~50%（需改造） |
| 工期（1 人） | **≈4 周** | 14~18 周 | 14~18 周 | 8~10 周 |
| 双端一致性 | 天然一致（同一份 Web） | 需处理平台差异 | 最好 | 好 |
| 原生体验 | 好（滚动/输入有轻微 Web 感） | 最好 | 最好 | 中 |
| 复杂表格/图表 | **直接复用 Element Plus + ECharts** | 需重写表格与图表 | 需重写 | 组件生态弱 |
| 后续维护成本 | **低**（一套代码） | 高（两套 UI） | 高（两套 UI） | 中 |
| 原生能力 | 插件齐全（推送/相机/文件/生物识别） | 齐全 | 齐全 | 齐全 |
| 适合场景 | 管理后台、内容型 App | 高频交互 C 端 | 高性能 C 端 | 多端小程序矩阵 |

**为什么不是 D（uni-app）**：它擅长「一套代码出小程序 + App」，但我们的小程序是给顾客的商城，后台是给商家的调度台，两者页面完全不同，复用不了；而 uni-app 的表格/图表组件在复杂后台场景下比 Element Plus 弱不少。

## 四、推荐架构

```
┌───────────────────────────────────────────────┐
│  admin-web/   （唯一业务源码，Vue 3）          │
│  ├─ src/views/*        11 个页面               │
│  ├─ src/api/*          接口层（axios）         │
│  ├─ src/styles/mobile.css   移动端适配层       │
│  └─ dist/              构建产物                │
└──────────────────┬────────────────────────────┘
                   │  npx cap sync（把 dist 拷进原生工程）
        ┌──────────┴───────────┐
        ▼                      ▼
┌───────────────┐      ┌───────────────┐
│ android/      │      │ ios/          │
│ Gradle + 签名  │      │ Xcode + 证书  │
│ → APK / AAB   │      │ → IPA         │
└───────┬───────┘      └───────┬───────┘
        │  原生能力（Capacitor 插件）    │
        ├─ 推送（订单提醒）
        ├─ 语音播报（TTS）
        ├─ 文件选择（批量导入）
        ├─ 安全存储（JWT → Keychain/Keystore）
        └─ 返回键 / 状态栏 / 安全区
                   │
                   ▼
        后端 API（云托管，无需改动业务）
```

### 目录结构（新增部分）

```
admin-app/                 # 新增：原生壳工程（不含业务代码）
├─ package.json            # 只装 capacitor 依赖
├─ capacitor.config.ts     # appId / appName / webDir=../admin-web/dist
├─ android/                # Gradle 工程（自动生成后入库）
└─ ios/                    # Xcode 工程（自动生成后入库）
```

> 关键点：**业务代码永远只在 `admin-web/`**，`admin-app/` 只放原生壳。这样 Web 与 App 不会分叉。

## 五、必须解决的 8 个技术点

| # | 问题 | 做法 |
| --- | --- | --- |
| 1 | **接口地址** | 构建时注入 `VITE_API_BASE=https://<生产域名>/api`；Web 端仍走 `/api` 相对路径（nginx 反代），两端互不影响 |
| 2 | **跨域（CORS）** | App 内 WebView 的 Origin 是 `https://localhost` / `capacitor://localhost`，后端白名单需放行；否则 App 内所有请求 403（**这是混合方案最容易踩的坑**） |
| 3 | **登录态存储** | Web 用 `localStorage`；App 内改用 `@capacitor/preferences` + 加密存储（Android Keystore / iOS Keychain），避免明文 |
| 4 | **订单推送** | `@capacitor/push-notifications`。Android 国内必须接厂商通道（华为/小米/OPPO/vivo）→ 建议直接上**极光 JPush** 或**个推**，一次接入覆盖双端；iOS 走 APNs |
| 5 | **语音播报** | Web 的 `speechSynthesis` 在部分安卓 WebView 没有中文语音包 → App 内改用原生 TTS 插件（`@capacitor-community/text-to-speech`） |
| 6 | **批量导入选文件** | Web 用 `<input type="file">`；App 内改用 `@capacitor/filesystem` + 原生文件选择器，Excel 解析逻辑不变 |
| 7 | **返回键** | Android 物理返回键：非首页 → 路由后退；首页 → 二次确认退出（`@capacitor/app` 的 `backButton`） |
| 8 | **热更新** | Web 资源可热更（Capacitor Updater / 自建），原生壳发版才需要走商店。**建议只对 Web 层热更**，原生依赖变更仍走商店 |

## 六、页面 × 移动端形态映射

| 页面 | 手机形态 | 说明 |
| --- | --- | --- |
| 登录 | 单列表单 | 记住账号；密码可见切换；键盘不遮挡按钮 |
| 营业大盘 | 读数 2×3 + 全宽图表 | 六格读数改两列；趋势图横滑看时间轴；TOP 榜单改列表；搜索分析可折叠 |
| 订单管理 | **卡片流** | 卡片含单号/用户/金额/状态/时间；操作：详情·发货·同步·售后；下拉刷新 + 触底加载 |
| 售后管理 | **卡片流** | 商品缩略图 + 原因 + 退款额 + 同意/拒绝（危险操作二次确认） |
| 商品管理 | **卡片流** | 图 + 名称 + 价格 + 库存 + 上下架；点击进编辑页 |
| 批量导入 | 分步表单 | 选文件 → 校验预览 → 提交；错误行高亮 |
| 分类管理 | 列表 + 行内编辑 | 拖拽排序在移动端改为上移/下移按钮 |
| 库存管理 | 两列卡片 | SKU 规格 + 库存步进器，就地改数 |
| 用户管理 | 卡片 | 头像 + 昵称 + 订单数/消费额 + 只看他 |
| 用户访问 | 3 个 Tab + 紧凑表格 | 与 Web 同结构，表格字号降一档 |
| 配置管理 | 分组表单 | 公告内容、退款自动同意时长 |

**统一的移动端交互约定**：触控目标 ≥44px、详情用整页而非弹窗、危险操作原生确认框、下拉刷新、底部安全区留白。

| 阶段 | 内容 | 人日 | 产出 |
| --- | --- | --- | --- |

## 八、分发与合规

| 平台 | 方式 | 成本 | 备注 |
| --- | --- | --- | --- |
| Android（内测） | APK 直接安装 / 蒲公英 | 免费 | 最快，适合先给商家用起来 |
| Android（商店） | 华为/小米/OPPO/vivo/应用宝 | 免费，需**软著** | 软著加急约 3~5 工作日 |
| Google Play | AAB 上传 | $25 一次性 | 需海外开发者主体 |
| iOS（内测） | TestFlight | Apple 开发者 $99/年 | 内部 100 人、外部 10000 人 |
| iOS（商店） | App Store | 同上 | 商家后台类 App 可能被按 4.2「功能单一」问询，需说明 B2B 属性 |
| iOS（企业内） | Apple Business Manager 自定 App | 同上 | 不上公开商店，适合只给自己的商家用 |

**合规清单**：隐私政策页、权限用途说明（通知/文件/相机）、账号注销入口、个人信息收集清单。

## 九、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| WebView 内表格横向滚动体验差 | 中 | 订单/商品/售后改卡片流，其余保留表格并降密度 |
| 安卓厂商杀后台导致推送收不到 | 高 | 接厂商通道（极光/个推），引导用户加白名单 |
| iOS 审核被拒（B2B 后台） | 中 | 首选 TestFlight / ABM 自定分发，不强行上公开商店 |
| WebView 版本碎片（老旧安卓） | 中 | 最低 Android 8.0；关键 API 做特性检测降级 |
| 证书/签名丢失 | 高 | keystore 与 p12 入库加密备份，记录密码 |
| Web 与 App 版本漂移 | 低 | 同源构建 + Web 层热更，版本号统一 |
